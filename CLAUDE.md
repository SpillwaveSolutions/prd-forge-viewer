# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this repository holds

This repository has no application code yet. It holds one PRD for the PRD Forge
Viewer, a desktop app that reads, searches, and exports PRD sets made by the PRD
Forge plugin (`SpillwaveSolutions/prd-forge`). The PRD is the only source of
truth for what to build.

- `docs/prd/prd-forge-viewer/`: the PRD set. `prd.md` is the root, and 17
  section documents follow it in `order`.
- `docs/prd/prd-forge-viewer/grades/`: the reasons behind each section's grade.
  The PRD pane opens these when you click a grade.
- `docs/prd/prd-forge-viewer/diagrams/`: journey diagrams (Mermaid) and
  wireframe drawings (PlantUML Salt), generated by the plugin.
- `prd-forge-viewer-prd.pdf` and `.docx`: the export for stakeholders. Generated;
  do not edit.
- `projects/`: ArcKit design documents derived from the PRD. The PRD stays the
  source of truth. If the PRD changes, update these documents from it, not the
  other way around.
  - `000-global/ARC-000-PRIN-v1.0.md`: the 16 architecture principles.
  - `001-prd-forge-viewer/`: stakeholders (STKE), requirements (REQ), data
    model (DATA), `decisions/` (ADR-001 to ADR-005), `diagrams/` (DIAG-001 to
    DIAG-004), the HLD review (`vendors/internal/`), and traceability (TRAC).
  - `001-prd-forge-viewer/external/`: a copy of the PRD export that ArcKit
    reads. Copy the new PDF here after each export.
- In REQ, FR-001 to FR-024 are the PRD IDs with the PRD text. NFRs use ArcKit
  IDs (for example NFR-P-002) with a **PRD Source** field (NFR-002).

## Commands

This project installs the PRD Forge plugin at project scope from GitHub. Its scripts live
in the plugin cache, under the installed version:

```bash
P=~/.claude/plugins/cache/prd-forge/prd-forge/$(claude plugin list | awk '/prd-forge@/{f=1} f&&/Version/{print $2; exit}')
SET=docs/prd/prd-forge-viewer

node $P/scripts/prd-validate.mjs $SET          # schema, links, and id references
node $P/scripts/prd-diagrams.mjs $SET          # draw and render diagrams
python3 $P/scripts/prd_export.py $SET          # write the PDF and .docx
```

- Run the validator after every edit to a PRD document. It must report
  "18 documents, no errors".
- The export needs the Python packages `python-docx` and `pyyaml`.
- The diagram script needs `mmdc` and `plantuml` on the PATH.
- In Claude Code, `/prd` opens the stepper pane and `/prd-step` moves through
  it. The pane resolves `docs/prd` against the session's working directory.
  Do not `cd` into the set directory, or `/prd` reports that it finds no PRD set.
  The pane does not reread files on change. Click **Rescan** after edits.

## How the PRD works

- Change PRD content through the `prd-forge:prd-wizard` skill. It interviews the
  owner, grades each section, and keeps the links and statuses correct.
- The YAML front matter is the machine-readable record and is authoritative.
  The markdown body repeats it for people. Keep both consistent.
- Links between documents live only in front matter (`links.parent`, `prev`,
  `next`, `children`, `related`). The root's `links.children` carries each
  section's `status`, so update it when a section's status changes.
- Only a grading pass writes `score`, `blocking`, and `graded`, with a
  matching file in `grades/`. A section moves to `review` at a score of 70 or
  more with 0 blocking defects. It moves to `final` only with an approval in the
  change log (`16-change-log.md`).
- IDs are stable and never renumbered: `P-`, `PER-`, `O-`, `J-`, `ST-`, `SC-`,
  `IN-`, `OUT-`, `FR-`, `NFR-`, `C-`, `TR-`, `A-`, `R-`, `D-`, `Q-`, `REL-`,
  `WF-`. Cross-references between sections use these IDs.
- The PRD names no technology. It says "authoring tools" for PRD Forge in Claude
  Code. File formats appear only in scope item IN-006 (PDF and .docx). Keep
  technology choices for ADRs.

## Decisions already made

These come from the PRD owner and are recorded in the set. Do not reopen them
without the owner.

- The viewer is read-only in release 1, and editing is out of scope (OUT-001).
  C-002 is retired. The PRD owner revisits editing on 2026-11-06.
- Release 1 (REL-001, 2026-11-06) covers FR-001 to FR-024, except FR-006. Grade findings come
  in release 2 (REL-002, 2026-11-06).
- Every export shows "Draft" until every document is `final` (TR-005).
- The terminal command is `prdf` (FR-021). It remembers known PRD set locations
  (FR-022). When `docs/prd` holds more than one set, the viewer reopens the
  last one, or lists them the first time (FR-024).
- Release 1 runs on macOS only (OUT-003). C-004 is retired.
- The viewer shows only local content. No script runs, and nothing remote
  loads (NFR-010).

## Architecture decisions

The ADRs are in `projects/001-prd-forge-viewer/decisions/`. All are Accepted
(version 1.1, 2026-10-26).

1. ADR-001: Tauri 2 desktop app with the Motion stack and plugins.
2. ADR-002: Reuse the Motion themes and Word writer (Motion is MIT licensed).
   Write the PDF from themed HTML, so that fonts are embedded and the PDF is
   tagged for screen readers. The NFR-U-002 test picks the print engine.
3. ADR-003: BM25 ranking in a local SQLite full-text index (FTS5), one derived
   cache file for each set in the app data folder.
4. ADR-004: The app installs the `prdf` launcher. Known locations and themes
   live in one settings file in the OS app config folder.
5. ADR-005: OS file events with a per-file debounce and a polling fallback.

The HLD review (`ARC-001-HLDR-v1.1.md`) approves the design with no open
conditions. ADV-04 to ADV-06 are build tasks.

## Work tracking policy

- Every plan MUST end by running `worklog plan-capture` — it writes
  `docs/plans/<date>-<slug>.md` and appends the plan's steps as work items.
- Work discovered mid-flight that wasn't in the plan: run
  `worklog add --unplanned --discovered-during <item>` BEFORE doing the work.
- Never hand-edit `.work/*.jsonl` (use `worklog`) or `docs/roadmap.md`
  (it is generated; change the work items instead).
- After changing work items, run `worklog roadmap-render` and commit the log
  and roadmap together.
- One session per working directory. Two assistant sessions sharing a checkout
  switch branches under each other and solve the same problem twice; give each
  its own `git worktree`. `worklog` warns when it sees more than one, but the
  warning is advisory and arrives after the fact.
